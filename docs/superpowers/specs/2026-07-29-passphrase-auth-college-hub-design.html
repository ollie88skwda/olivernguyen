Why server-side, concretely

The hole this avoids. /studio's API routes carry GITHUB_TOKEN, which has read and write access to your private vault repo. If the passphrase were hardcoded client-side on /major the way go-fish is today, anyone could view-source, read it, and sign into /studio. That is repo write access, not just "someone saw my essays."

Today this is not a problem only because the two passphrases happen to differ. Unifying them is what creates the risk, so the check moves to the server in the same change.

Consequence to be aware of. One passphrase means signing in on /major also unlocks /studio. If you ever want to show /major to a counselor or a friend, handing over the passphrase hands over the vault too. If that comes up, the fix is a second passphrase with its own cookie — not in this change, but worth knowing before you share it.

Honest security posture

The last row matters. src/pages/apply/data.generated.js is 515 KB of school and program data compiled straight into the JS bundle, and REACT_APP_SUPABASE_ANON_KEY ships with it. Anyone who downloads a chunk has the data and a working Supabase key for the major_decision and apply_decision tables. Row Level Security on those two tables is the only thing actually controlling that access. The gate keeps the pages out of casual sight and nothing more — which is the same thing go-fish was doing, just without leaking the studio secret.

Checking RLS on those tables is a separate job, out of scope here, but it is the thing that would actually protect the data. Flagged, not fixed.

Architecture

The auth logic exists but is trapped inside src/pages/essay_studio/. The work is lifting it out, not writing it.

New shared module: src/auth/

  • store.js — small zustand store: checking, authed, error, apiMissing, check(), login(passphrase). Lifted verbatim from the studio store's auth half.
  • PassphraseGate.js — the form, moved from essay_studio/AuthGate.js. Gains one label prop so the eyebrow can read Route /major · private instead of being hardcoded to /studio.
  • RequireAuth.js — three states: checking → cream placeholder matching the existing Suspense fallback; apiMissing → the existing "run vercel dev" explainer; otherwise authed ? children : <PassphraseGate />.
<Route path="/major">
  <RequireAuth label="Route /major · private">
    <Major />
  </RequireAuth>
</Route>

New API route

api/auth/session.mjs — GET, returns 200 {ok:true} if requireSession() passes, otherwise its 401. Needed because the studio probes auth by calling /api/vault/list, and /major and /apply have no vault call to probe with. Roughly ten lines.

Unchanged on purpose

api/_lib/auth.mjs (jose HS256, HttpOnly studio_session cookie), api/auth/login.mjs (bcrypt compare), and all five vault and exemplar routes. Only the value of AUTH_PASSPHRASE_HASH changes. bcryptjs and jose stay as dependencies.

Environment

This GitHub repo is public (ollie88skwda/olivernguyen). So the passphrase and its bcrypt hash are kept out of every tracked file, including this spec. Writing them here would undo the entire reason for checking server-side.

.env.local is correctly gitignored and untracked. .env is tracked, but holds only REACT_APP_SUPABASE_URL and REACT_APP_SUPABASE_ANON_KEY — both REACT_APP_ vars that ship in the bundle anyway, so that is public by design rather than a leak. It does underline the RLS point above.

One value changes: AUTH_PASSPHRASE_HASH. Generate it locally, never commit it:

node -e "console.log(require('bcryptjs').hashSync(process.argv[1],10))" 'your-passphrase'

The result goes in .env.local and in the Vercel project for production, preview, and development. JWT_SECRET, GITHUB_*, and the Supabase vars are untouched.

Tradeoff you are accepting

/major and /apply currently run fine under react-scripts start. After this they need vercel dev, because the gate calls /api/auth/session and react-scripts start answers every path with index.html. The existing "start the site with vercel dev" explainer is reused rather than rewritten, so the failure mode is a clear message instead of a passphrase box that never opens.

The /college hub

Hero, then three cards — Major, Apply, Studio — each with a lock chip, since all three are gated now. Clicking any of them lands on the passphrase gate if you are signed out.

Copy is left as visible placeholders. The headline and the three card descriptions are your words. They render as obvious […] markers so nothing invented ships by accident.

Verification

Real browser, real vercel dev, per the project's E2E rule.

  1. Signed out, /college loads — hero and three cards, no gate.
  2. Signed out, /major gates — passphrase box reading Route /major · private. Confirms go-fish is gone: clearing localStorage and reloading must still gate.
  3. Grep the built bundle for the passphrase — must return nothing. Grep the tracked working tree too, since the repo is public. This is the check the whole server-side decision rests on.
  4. Wrong passphrase — "Not it. Try again." on all three pages.
  5. Correct passphrase on /major — page renders, Supabase doc loads, and /apply plus /studio are now open too on the same cookie.
  6. Signed out, API is closed — curl against /api/vault/list returns 401. The client gate is cosmetic; this is the one that matters.
  7. Studio still works end to end — a file opens, an edit autosaves, a real commit lands in the vault repo.
  8. Sidebar — College entry navigates on click and expands on +, at desktop and mobile widths.
  9. Hygiene — yarn build clean, no new lint warnings, existing Jest suites (model.test.js, portfolio.test.js, seed.test.js, vaultModel.test.js) still pass.

Out of scope

  • RLS on the Supabase tables — the real access control for /major and /apply data. Flagged above, not touched here.
  • The /debt sidebar link is dead — points at a route that does not exist in Routes.js, so it 404s. Pre-existing and unrelated; flagged, not fixed.
  • No logout button. Not asked for, and the cookie expires in 7 days.
