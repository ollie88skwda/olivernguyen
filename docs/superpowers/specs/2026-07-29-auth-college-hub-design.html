Split Auth
+ College Hub

Clerk on /studio, a shared passphrase on /major and /apply, and a public /college hub in the sidebar. Two gates because the two surfaces need different things, not because of drift.

The shape

RouteGateWhy that one
/collegeNone — publicThe shop window. Links to the other three.
/majorPassphrase, server-verifiedLow friction, no account needed, shareable if you decide to.
/applyPassphrase, server-verifiedSame. Shares one cookie with /major.
/studioClerkReal identity, revocable sessions, no shared secret. This is the one whose API routes hold GITHUB_TOKEN.

The split fixes the problem the earlier designs had. When one passphrase covered all three, the /major passphrase was the /studio passphrase, which is GitHub write access to the vault repo. Giving /studio its own identity provider removes that coupling entirely. Sharing the passphrase now costs you nothing but the two decision tools.

Honest security posture

SurfaceProtectionReal?
/studio vault reads and writesEvery api/vault/* and api/exemplars/* call verifies a Clerk session server-side, then checks the user ID against an allowlistYes. Genuine.
The passphrase itselfbcrypt hash in server env, compared server-sideYes. Never reaches the browser.
/major and /apply page accessGate blocks render until the cookie existsPage-level only.
/major and /apply dataNoneNo. See below.

src/pages/apply/data.generated.js is 515 KB of school and program data compiled into the JS bundle, and REACT_APP_SUPABASE_ANON_KEY ships with it — it is already committed in .env, which is fine, because REACT_APP_ vars are public by definition. Anyone with a bundle chunk has the data and a working key for the major_decision and apply_decision tables. Row Level Security on those two tables is the only real control. The passphrase keeps the pages out of casual sight and nothing more.

RLS on those tables is a separate job, out of scope here, but it is the thing that would actually protect that data. Flagged, not fixed.

This GitHub repo is public (ollie88skwda/olivernguyen). The passphrase and its bcrypt hash appear in no tracked file, including this spec, and must stay that way.

Architecture

Server: two libs, cleanly divided

All five existing requireSession() call sites are vault or exemplar routes — every one of them /studio. So api/_lib/auth.mjs becomes Clerk's, and the passphrase moves to its own file with its own cookie. Nothing shares state.

LibGuardsCookie
api/_lib/auth.mjs (rewritten)api/vault/*, api/exemplars/*Clerk's __session
api/_lib/passphrase.mjs (new)api/auth/login, api/auth/sessiongate_session — renamed from studio_session, which is now a misnomer

requireSession(req, res) keeps its exact name and signature in the rewritten auth.mjs, so the five call sites are not edited — only the verification behind them changes:

import { verifyToken } from "@clerk/backend";

// 1. read the __session cookie
// 2. verifyToken(token, { secretKey: CLERK_SECRET_KEY, authorizedParties })  -> 401
// 3. payload.sub must be in CLERK_ALLOWED_USER_IDS                           -> 403
//    the 403 body echoes the rejected userId, so setup is one round trip

api/auth/login.mjs keeps its bcrypt logic unchanged; only its import moves to passphrase.mjs. api/auth/session.mjs is new — a cheap GET returning 200 or 401, needed because /major and /apply have no data call to probe auth with.

To confirm against the installed package, not assumed: verifyToken's return shape. The docs show a try/catch example but type it as JwtReturnType, which is a { data, errors } object in newer releases. The installed version gets read before this is written.

Client

Package is @clerk/react. Two things changed recently and contradict older tutorials: it is no longer @clerk/clerk-react, and <SignedIn> / <SignedOut> are deprecated in favour of <Show when="signed-in">. Under CRA the key is read from REACT_APP_CLERK_PUBLISHABLE_KEY automatically and is not passed as a prop.

ClerkProvider sits inside <Router>, since router integration needs useHistory():

<ClerkProvider
  afterSignOutUrl="/college"
  routerPush={(to) => history.push(to)}
  routerReplace={(to) => history.replace(to)}
/>

Guard against the missing-key crash. ClerkProvider throws when the publishable key is absent, which would take down /college, /major and /apply too. So it mounts only when the key exists; without it those three work normally and /studio shows a "Clerk not configured" explainer. That means the passphrase half ships and works before you touch the Clerk dashboard — you are not blocked.

Build order

Sequenced so nothing is blocked on the Clerk dashboard.

  1. Passphrase half — split the libs, lift the gate, wrap /major and /apply, delete both go-fish blocks. Fully testable today.
  2. Hub and sidebar — /college, the College nav entry, back-links. No auth dependency.
  3. Clerk half — provider, /sign-in, RequireClerk, rewritten auth.mjs. Ships inert until the keys exist, then switches on.

Verification

Real browser, real vercel dev, per the project's E2E rule.

  1. Signed out, /college loads — hero and three cards, no gate.
  2. Signed out, /major gates — box reads Route /major · private. Clear localStorage and reload: must still gate, proving go-fish is gone.
  3. Grep the built bundle and the tracked tree for the passphrase — must return nothing. The check the server-side decision rests on.
  4. Wrong passphrase — "Not it. Try again."
  5. Correct passphrase on /major — renders, Supabase doc loads, and /apply is open on the same cookie. /studio is not — that is the whole point of the split.
  6. No Clerk keys set — /college, /major, /apply all work; /studio shows the explainer rather than a white screen.
  7. Clerk keys set, signed out — /studio redirects to /sign-in; curl on /api/vault/list returns 401.
  8. Clerk signed in, not yet allowlisted — /api/vault/list returns 403 with the userId in the body. Both a test and the setup step.
  9. Allowlisted — vault loads, a file opens, an edit autosaves and lands a real commit.
  10. Sidebar — College entry navigates on click, expands on +, at desktop and mobile widths.
  11. Hygiene — yarn build clean, no new lint warnings, existing Jest suites (model.test.js, portfolio.test.js, seed.test.js, vaultModel.test.js) pass.

Tradeoffs accepted

  • Two auth systems. Justified here — different surfaces, different privacy needs — but it is two things to maintain, and bcryptjs, jose, @clerk/react and @clerk/backend all stay in the tree.
  • /major and /apply now need vercel dev locally. They run on react-scripts start today. With /studio on Clerk, the original security reason for server-verifying the passphrase is gone, so a client-side gate would now be defensible and would keep react-scripts start working. Server-side is kept anyway because the env is already configured and it keeps the passphrase out of the bundle — say the word to flip it.
  • CRA 5 and modern package exports. @clerk/react targets modern bundlers; webpack 5 should resolve it, but source-map warnings from node_modules are likely. Cosmetic if so; a real resolution failure would be a blocker and would change the approach.
  • Clerk appearance API drift. Theming maps to Clerk's internal element keys. A Clerk update can change them. Failure mode is ugly, not broken.

The /college hub

Hero, then three cards. Each carries a lock chip, and clicking through lands on whichever gate applies.

Copy is left as visible placeholders. The headline and the three card descriptions are your words. They render as obvious […] markers so nothing invented ships by accident.

Out of scope

  • RLS on the Supabase tables — the real access control for /major and /apply data. Flagged above, not touched.
  • The /debt sidebar link is dead — points at a route that does not exist in Routes.js. Pre-existing and unrelated; flagged, not fixed.
  • No logout for the passphrase gate. The cookie expires in 7 days. Clerk brings its own via <UserButton />.

Your steps

  1. Done — AUTH_PASSPHRASE_HASH set in all three Vercel environments.
  2. Create a Clerk application at dashboard.clerk.com. Email sign-in.
  3. Turn sign-up off — Configure → Restrictions. Clerk allows open registration by default; this is the lock that matters most.
  4. Create your user manually — Users → Create user.
  5. Add both Clerk keys to Vercel, and add your production domain to the Clerk instance so cookies work on olivernguyen.com.
  6. Sign in once, read the userId from the 403, set CLERK_ALLOWED_USER_IDS.
  7. Write the hub copy — headline plus three card descriptions.
