Moving The Site
To Vercel

Yes — the /api routes start working by themselves on Vercel. There is no code to port. This is a DNS change plus merging the studio branch.

Why the API just works

Your api/*.mjs files are already written in Vercel's zero-config format: one file per route, default-exported handler(req, res). Vercel finds them automatically. That is why the studio worked under vercel dev and nowhere else.

Cloudflare Pages does not use that format. It wants a functions/ folder with onRequest(context) handlers. You don't have one, so on Cloudflare /api/vault/list falls through to the SPA and returns HTML.

Already true, nothing to do: the Vercel project olivernguyen exists and has working production deployments, the domain is already on your Vercel account, and all five studio secrets (GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO, JWT_SECRET, AUTH_PASSPHRASE_HASH) are already set for Production.

The zone holds nothing but the website. No email, no verification records. That makes this about as low-risk as a domain move gets.

The steps

Part 1 — Point the domain at Vercel

  1. Open the Vercel project → olivernguyen → Settings → Domains. Add olivernguyen.com and www.olivernguyen.com.

    Vercel will show you the exact DNS records it wants. Use the values it shows you, not values from a blog post — Vercel has changed its recommended apex IP before.

  2. In Cloudflare → DNS → Records, replace the apex A record with the one Vercel gave you, and point www at the Vercel target (usually a CNAME to cname.vercel-dns.com).
  3. Set both records to "DNS only" — click the orange cloud so it turns grey.

    This is the step people miss. If Cloudflare keeps proxying, Vercel cannot issue an SSL certificate and the site breaks with a cert error.

  4. Wait for Vercel to say "Valid Configuration" on the Domains page. Usually a few minutes. Vercel issues the certificate on its own once it can see the records.

Part 2 — Stop Cloudflare from serving the site

  1. Cloudflare dashboard → Workers & Pages → your Pages project → Settings. Remove olivernguyen.com from its custom domains.
  2. Disconnect the GitHub integration on that Pages project, or delete the project.

    Otherwise every push builds twice — once on Cloudflare, once on Vercel — and the two can fight over the domain.

Part 3 — Ship the studio

  1. Merge the branch and push. Vercel builds on push, same as Cloudflare did. 
    cd ~/Documents/Code/olivernguyen
git checkout main
git merge redesign/essay-studio
git push origin main
  2. Watch the deploy in the Vercel dashboard, or run vercel ls.

Two things to watch

Deployment Protection is on. Your *.vercel.app URLs currently redirect to a Vercel login (302). That is normally fine — custom production domains stay public — but if olivernguyen.com asks you to log in after the move, turn it off under Settings → Deployment Protection.

The studio is private by passphrase only. Once it is on a public domain, /studio is reachable by anyone who knows the URL, and the only thing in front of your essays is the passphrase. It is unlinked from the site nav, and the API checks a signed cookie on every call — but it is worth knowing that "not linked" is not the same as "not reachable".

Optional: move DNS to Vercel too

The steps above leave DNS at Cloudflare, which is the fastest route and is fully "hosted on Vercel". If you want DNS there as well, change the nameservers at Squarespace to Vercel's, then re-add the records in Vercel. Since the zone has no email and no TXT records, nothing else has to be recreated. Do it after the site is confirmed working, not at the same time — one change at a time makes it obvious what broke.
