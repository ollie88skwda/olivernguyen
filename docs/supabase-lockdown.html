Closing The
Supabase Hole

Right now anyone can overwrite or delete your /major and /apply documents. The code fix is written and committed. What is left is four things only you can do, in a specific order.

What is wrong, in one paragraph

Your two decision tables have Row Level Security switched on, which sounds safe. But the policies say USING (true) for the anon role, on ALL commands. That means the anonymous role can read, update and delete every row. Your anon key is printed in .env in a public GitHub repo and also shipped inside your JavaScript bundle. So the key is not a secret, and the policy grants that non-secret key full write access. Anyone who views source can wipe your college document.

Why the passphrase does not help. The passphrase lives in a cookie on your API. Supabase has never heard of it. From Supabase's point of view your browser is just an anonymous visitor — exactly like everyone else's. There is no way to write a policy that tells you apart, which is why the fix has to move the write somewhere the passphrase is known.

The order matters

Do not run the SQL first. Your live site today writes to Supabase directly with the anon key. The moment you drop those policies, saving breaks on the deployed /major — and it stays broken until the new code is deployed. Deploy first, then drop.

If you would rather be safe than functional for a day, that is a legitimate choice — just make it knowingly. Read-only for a day beats losing the document.

Step by step

  1. Get the service-role key

    Open your project's API keys page.

    Find the key labelled service_role (older projects) or one starting sb_secret_ (newer). Either works. Click reveal, then copy it.

    This key ignores every security rule in your database. Treat it like a password. It goes only into .env.local and Vercel. It must never start with REACT_APP_, never appear in anything under src/, and never be committed — your repo is public.

  2. Put the key where the server can read it

    Add it to your local file. In Terminal, from the project folder — replace PASTE_KEY_HERE with what you copied:

    echo 'SUPABASE_SERVICE_ROLE_KEY="PASTE_KEY_HERE"' >> .env.local

    Then add it to Vercel, all three environments:

    vercel env add SUPABASE_SERVICE_ROLE_KEY production  --value "PASTE_KEY_HERE" --yes --force
vercel env add SUPABASE_SERVICE_ROLE_KEY preview     --value "PASTE_KEY_HERE" --yes --force
vercel env add SUPABASE_SERVICE_ROLE_KEY development --value "PASTE_KEY_HERE" --yes --force

    Check it worked:

    vercel env ls | grep SUPABASE_SERVICE_ROLE_KEY

    You should see three lines. If you see none, the command failed — look for an error above it.

  3. Test locally, then deploy

    Start the site:

    npm run dev:vercel

    Wait for Compiled successfully, then open http://localhost:3000/major, enter the passphrase, turn on EDIT and change something.

    It worked if the timestamp in the corner updates to SAVED HH:MM. Reload the page — your change should still be there. That proves the write went through the new endpoint.

    If it fails, open the browser console. 500 SUPABASE_SERVICE_ROLE_KEY is missing means step 2 did not take — check the spelling in .env.local and restart the server.

    Deploying is blocked right now. Your /apply page has never been committed to git, and the auth branch depends on it — see docs/handoff-apply.html. That question has to be settled before anything reaches production. Do not skip ahead to step 4 until a deploy has actually gone out.

  4. Only after deploying — close the hole

    Open the SQL editor. Paste this and run it:

    drop policy "anon can write apply_decision" on public.apply_decision;
drop policy "anon can write major_decision" on public.major_decision;

    Then check what is left:

    select tablename, policyname, cmd, roles::text
from pg_policies
where schemaname = 'public'
  and tablename in ('apply_decision','major_decision');

    You should see exactly two rows, both SELECT, both {anon}. If any row still says ALL, that table is still writable by anyone — stop and fix it.

    Keeping the two SELECT policies is deliberate: page loading and live-sync need them, and the data is already inside your public JavaScript bundle, so reading adds nothing new. What you have removed is the ability for a stranger to change anything.

  5. Confirm it is actually fixed

    Prove a stranger cannot write. Paste this in Terminal — it uses only your public anon key, exactly what an attacker has:

    ANON=$(grep '^REACT_APP_SUPABASE_ANON_KEY=' .env | cut -d= -f2- | tr -d '"')
curl -s -o /dev/null -w 'anon write -> HTTP %{http_code}\n' \
  -X POST 'https://lhiwhmcdqqwwurectxos.supabase.co/rest/v1/major_decision' \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON" \
  -H 'Content-Type: application/json' -H 'Prefer: resolution=merge-duplicates' \
  -d '{"id":"v1","doc":{"hacked":true},"updated_at":"2030-01-01T00:00:00Z"}'

    Expect 401 or 403. If you get 200 or 201, the policy did not drop — go back to step 4.

    If that command returns 200 before you have done step 4, that is not a test failure — that is the live vulnerability, and it just overwrote your document with {"hacked":true}. Only run this check after step 4.

    Then confirm you can still save on the deployed /major: enter the passphrase, edit something, watch for SAVED, reload.

One more table to decide about

pull_picks, behind your /pull page, is open to the public role for SELECT, INSERT, UPDATE and DELETE.

Public insert is probably deliberate — that is how friends submit picks. Public delete almost certainly is not: anyone can erase everyone's votes. If you agree, run:

drop policy "Public delete" on public.pull_picks;

This one is safe to run immediately — nothing in your code deletes from that table, so nothing breaks. Public UPDATE is also worth a thought later: it currently lets anyone rewrite someone else's pick.
