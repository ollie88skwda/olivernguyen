Closing The
Supabase Hole

Right now anyone can overwrite or delete your /major and /apply documents. The code fix is written and committed. What is left is four things only you can do, in a specific order.

Closed and verified 2026-07-30. Every step below has been carried out. The results, measured against production with the public anon key — exactly what an attacker holds:

INSERT, UPSERT and DELETE on all three tables → 401. PATCH and unfiltered DELETE → 204 affecting zero rows (PostgREST returns 204 when RLS leaves nothing visible to modify — this is a pass, not a hole). Confirmed against the data rather than the status codes: pull_picks still holds 7 rows, neither document gained a hacked key, both updated_at values are unchanged, and no probe row survived anywhere. SELECT still returns 200 on all three, so the pages still load.

One thing remains unverified and only you can do it: enter the passphrase on production /major, edit something, and confirm it reaches SAVED. That exercises the passphrase cookie path, which no automated check here can reach. It also settles the open question from docs/handoff-apply.html — AUTH_PASSPHRASE_HASH on production is write-only in Vercel, so it was re-pushed from the known-good local value but never read back and compared.

What is wrong, in one paragraph

Your two decision tables have Row Level Security switched on, which sounds safe. But the policies say USING (true) for the anon role, on ALL commands. That means the anonymous role can read, update and delete every row. Your anon key is printed in .env in a public GitHub repo and also shipped inside your JavaScript bundle. So the key is not a secret, and the policy grants that non-secret key full write access. Anyone who views source can wipe your college document.

Why the passphrase does not help. The passphrase lives in a cookie on your API. Supabase has never heard of it. From Supabase's point of view your browser is just an anonymous visitor — exactly like everyone else's. There is no way to write a policy that tells you apart, which is why the fix has to move the write somewhere the passphrase is known.

The order matters

Do not run the SQL first. Your live site today writes to Supabase directly with the anon key. The moment you drop those policies, saving breaks on the deployed /major — and it stays broken until the new code is deployed. Deploy first, then drop.

If you would rather be safe than functional for a day, that is a legitimate choice — just make it knowingly. Read-only for a day beats losing the document.

Step by step

  1. Get the service-role key

    Open your project's API keys page.

    Find the key labelled service_role (older projects) or one starting sb_secret_ (newer). Either works. Click reveal, then copy it.

    This key ignores every security rule in your database. Treat it like a password. It goes only into .env.local and Vercel. It must never start with REACT_APP_, never appear in anything under src/, and never be committed — your repo is public.

  2. Put the key where the server can read it

    Add it to your local file. In Terminal, from the project folder — replace PASTE_KEY_HERE with what you copied:

    echo 'SUPABASE_SERVICE_ROLE_KEY="PASTE_KEY_HERE"' >> .env.local

    Then add it to Vercel, all three environments:

    vercel env add SUPABASE_SERVICE_ROLE_KEY production  --value "PASTE_KEY_HERE" --yes --force
vercel env add SUPABASE_SERVICE_ROLE_KEY preview     --value "PASTE_KEY_HERE" --yes --force
vercel env add SUPABASE_SERVICE_ROLE_KEY development --value "PASTE_KEY_HERE" --yes --force

    A second variable is needed, and this guide originally missed it. Both routes also read process.env.REACT_APP_SUPABASE_URL. That currently lives only in the committed .env, which Create React App reads at build time to bake into the browser bundle. Vercel does not feed a committed .env to functions at runtime, and vercel.json has no env block, so in production the value would be undefined and createClient() would throw before it ever reached your database.

    The URL is not a secret — it is already in the public bundle — so paste it literally:

    vercel env add REACT_APP_SUPABASE_URL production  --value "https://lhiwhmcdqqwwurectxos.supabase.co" --yes --force
vercel env add REACT_APP_SUPABASE_URL preview     --value "https://lhiwhmcdqqwwurectxos.supabase.co" --yes --force
vercel env add REACT_APP_SUPABASE_URL development --value "https://lhiwhmcdqqwwurectxos.supabase.co" --yes --force

    Check both worked:

    vercel env ls | grep -E 'SUPABASE_SERVICE_ROLE_KEY|REACT_APP_SUPABASE_URL'

    You should see six lines — three for each. If you see none, the command failed — look for an error above it.

    While you are in there: the two NEXT_PUBLIC_SUPABASE_* variables on Production are 124 days old, left over from when this project was assumed to be Next.js. Nothing reads them. Harmless, but safe to delete.

  3. Test locally, then deploy

    Start the site:

    npm run dev:vercel

    Wait for Compiled successfully, then open http://localhost:3000/major, enter the passphrase, turn on EDIT and change something.

    It worked if the timestamp in the corner updates to SAVED HH:MM. Reload the page — your change should still be there. That proves the write went through the new endpoint.

    If it fails, open the browser console. 500 SUPABASE_SERVICE_ROLE_KEY is missing means step 2 did not take — check the spelling in .env.local and restart the server.

    The git blocker is gone. Oliver approved /apply entering public history on 2026-07-30, so main has been fast-forwarded onto the auth work — 18 commits, 78 files, verified free of junk paths and secrets, 105 tests passing, build clean. feat/split-auth-college-hub is deleted. No rebase was needed: main was already a strict ancestor.

    Nothing has been pushed, deliberately. Pushing triggers a production deploy, and the deployed /major would then save through the new endpoint — which returns 500 until step 2 is done. So step 2 gates the push, and the push gates step 4. Do not skip ahead to step 4 until a deploy has actually gone out.

  4. Only after deploying — close the hole

    Open the SQL editor. Paste this and run it:

    -- decision docs: writes now go through /api/decision/save (service role + passphrase gate)
drop policy "anon can write apply_decision" on public.apply_decision;
drop policy "anon can write major_decision" on public.major_decision;

-- pull picks: writes now go through /api/pull/pick (service role + validation)
drop policy "Public write"  on public.pull_picks;   -- INSERT
drop policy "Public update" on public.pull_picks;   -- UPDATE
drop policy "Public delete" on public.pull_picks;   -- DELETE

    Then check what is left:

    select tablename, policyname, cmd, roles::text
from pg_policies
where schemaname = 'public'
  and tablename in ('apply_decision','major_decision','pull_picks');

    You should see exactly three rows, all SELECT. If any row still says ALL, INSERT, UPDATE or DELETE, that table is still writable by anyone — stop and fix it.

    Keeping the two SELECT policies is deliberate: page loading and live-sync need them, and the data is already inside your public JavaScript bundle, so reading adds nothing new. What you have removed is the ability for a stranger to change anything.

  5. Confirm it is actually fixed

    Prove a stranger cannot write. Paste this in Terminal — it uses only your public anon key, exactly what an attacker has:

    ANON=$(grep '^REACT_APP_SUPABASE_ANON_KEY=' .env | cut -d= -f2- | tr -d '"')
curl -s -o /dev/null -w 'anon write -> HTTP %{http_code}\n' \
  -X POST 'https://lhiwhmcdqqwwurectxos.supabase.co/rest/v1/major_decision' \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON" \
  -H 'Content-Type: application/json' -H 'Prefer: resolution=merge-duplicates' \
  -d '{"id":"v1","doc":{"hacked":true},"updated_at":"2030-01-01T00:00:00Z"}'

    Expect 401 or 403. If you get 200 or 201, the policy did not drop — go back to step 4.

    If that command returns 200 before you have done step 4, that is not a test failure — that is the live vulnerability, and it just overwrote your document with {"hacked":true}. Only run this check after step 4.

    Then confirm you can still save on the deployed /major: enter the passphrase, edit something, watch for SAVED, reload.

The third table — decided, and handled in code

pull_picks, behind your /pull page, was open to the public role for SELECT, INSERT, UPDATE and DELETE. Oliver confirmed on 2026-07-30 that this was not intentional, so its drops are folded into step 4 above rather than left as an optional extra.

Correcting this guide's earlier advice. It previously said dropping Public delete was “safe to run immediately — nothing in your code deletes from that table”. That was wrong. src/pages/pull.js did delete: clearing your own pick ran .delete().eq("player", …).eq("weekend", …). Dropping that policy on its own would have silently broken the clear-your-pick button.

The reason all three write policies can now go is api/pull/pick.mjs. /pull has no login — identity is just a name typed into localStorage — so unlike the decision routes there is no cookie to require. What the route does instead is remove every write primitive except the single one the page needs:

  • the weekend must parse, be a Saturday, and fall in 2025–2027;
  • the amount must be one of the five LEVELS values, or null to clear;
  • the player name must be non-empty and at most 40 characters;
  • both the upsert and the delete are scoped server-side to one (player, weekend) pair — the client never gets to say which rows are affected.

What is still possible, stated plainly: someone who knows a player's name can still change that player's pick. That is inherent to a page with no accounts. It is a far smaller blast radius than DELETE on the whole table, which is what anyone reading your JavaScript bundle had before.
